# Covenant: system explanation

Covenant is an underwriting workspace for the deal team of a private credit fund (the fictional Fernhill Credit Partners). It is a working prototype: every screen runs on realistic, internally consistent data, and the full path from a new CIM to an IC-approved, locked set of terms can be demonstrated end to end.

## 1. What I built

**One workspace for the whole underwriting process.** Deals, companies and people share one navigation. Each deal page carries the underwriting work in ten tabs, ordered by the deal lifecycle.

| Area | What it does |
|---|---|
| **Deals** | List with filters and saved columns; pipeline board where a drag runs the stage rules: missing items are listed, soft rules can be overridden with a recorded reason, and the move to Documentation requires IC approval. Passed deals keep a reason code, so they remain usable as precedents. |
| **Financials** | AI-extracted values sit beside the source page, with the passage highlighted and a confidence score. A person confirms or corrects each value. Correcting LTM EBITDA from the CIM's $17.5M to the QoE's $16.3M immediately moves leverage from 5.14x to 5.52x and cushion from 26.5% to 21.1%, and flags the memo sections that depend on it. |
| **Securities** | Versioned term sets (copy-on-write drafts, issue, compare any two versions), tranche terms, the leverage-covenant schedule with a headroom bar against the 25% cushion guideline, and sources & uses. IC approval locks the approved version. |
| **Due diligence** | Findings and requests by workstream. A red-flag finding can be turned into a proposed IC condition in one step; unresolved red flags block the move to IC. |
| **IC memo** | Eight sections in which every number is a live reference to the data, never typed text, so a correction can't leave a stale figure in the memo. Each section shows why it is stale, which records it cites and which queries produce it; it can be regenerated by Claude or offline, edited, and reviewed. Only a VP or MD can mark it ready, and only when no section is stale or unreviewed. |
| **IC & approvals** | The IC packet, per-member votes, Q&A, conditions and the decision; precedents from the fund's own closed and passed deals, with the questions IC asked at the time; devil's-advocate questions linked to those precedents. |
| **Chat** | Questions across the whole database ("What spreads did we approve on services deals over $75M, and why did we pass on similar ones?"), answered with citation chips and a "Show queries" trace. It is also available as a panel on each deal. |
| **Relationships** | Company and person pages with role history (e.g. Larch's CFO was previously CFO of a past borrower), sponsor track record, activity, notes with @-mentions, and duplicate checks when creating records. |

The demo uses four personas (Analyst, VP, MD, IC member). Permissions are enforced, and every change is written to an audit trail, which is what the History tab shows.

## 2. Architecture

```
 Browser (Next.js app)                                       Server
┌──────────────────────────────────────────────────┐      ┌─────────────────────────┐
│ UI ──► actions (permission check, write, audit)  │      │ /api/llm                │
│          │                                       │      │ thin proxy, no data     │
│          ▼                                       │      │   │                     │
│ Store (Zustand → localStorage)  = operational DB │      │   ▼                     │
│          │                                       │      │ Claude Messages API     │
│ Selectors (leverage, cushion, staleness, gates)  │      │ (claude-sonnet-5-5,     │
│ Query tools (14 typed reads) ◄── tool loop ──────┼─────►│  refusal fallback)      │
│          └──► offline engine (same tools)        │      └─────────────────────────┘
└──────────────────────────────────────────────────┘
```

- **The ontology lives in code.** `lib/schema.ts` defines the objects, `lib/actions.ts` the actions that change them (34 named actions such as `correctField`, `issueTermSet` and `decideIc`), and `lib/selectors.ts` the derived values. The UI never writes data directly.
- **AI answers by querying, not by searching files.** Claude is given 14 typed tools (deals, terms, financials, diligence, IC history, precedents, companies, people, activity, document pages). The browser runs each call against its store and returns compact JSON with citation tokens. This is the "extract first, then query" pattern; in production the same tools become an **MCP server over Postgres**.
- **It works without AI.** With no API key, chat answers the five demo question types by running the same queries, and the memo is regenerated from deterministic templates. A guard rejects any AI-written memo text that types a figure instead of a live reference.
- **Production path:**
  - an extraction pipeline with a human review queue feeding an operational Postgres database (the ontology and its actions);
  - this application layer and the MCP server reading from that database;
  - SSO and information walls;
  - integrations with the CRM, the data room and post-close systems;
  - a separate warehouse for analytics.

## 3. Data model

24 entities, each validated with zod; `docs/schema.sql` is the Postgres equivalent.

- **Relationship layer:** Company, Person, Affiliation (role history), Stakeholder (deal role), Note, User.
- **Underwriting core:** Deal, StageEvent, Document, ExtractedField, FinancialPeriod, TermSet, Tranche, Covenant, DDItem, Memo, MemoSection, ICEvent, ICCondition, DevilsAdvocate.
- **Cross-cutting:** AuditEvent, ChatThread, ChatMessage, Settings.

Five rules hold throughout:

1. Displayed numbers are computed from confirmed records, never typed.
2. Term sets are copy-on-write, and IC approval locks them.
3. Every write produces an AuditEvent.
4. Risk ratings are stored with their scale.
5. Duplicate checks run before a company or person is created.

The seed holds 12 deals at every stage (Project Larch fully built), 25 companies and 40 people. Its numbers tie out (sources = uses, leverage and cushion consistent with the covenant schedule), and 69 unit tests check the calculations, stage rules, permissions and seed integrity.

## 4. Tradeoffs

| | |
|---|---|
| **Mocked** | Sign-in (persona picker in place of SSO); CIM extraction (a staged animation over a sample CIM, with pre-written proposed values and confidence scores); documents are Markdown pages rather than PDFs. |
| **Simplified** | The database is the browser's localStorage (one user, no concurrency); permissions are four roles rather than per-deal teams; one financial covenant type; precedent similarity is a simple score on sector tags, size and leverage; relationship strength counts notes and roles. |
| **Skipped** | Information walls and MNPI controls, email and calendar capture, data-room sync, Word export, closing checklist and post-close handoff, firm-configurable stages and templates, multi-user real-time editing. |

## 5. With a couple more days

1. **Real extraction:** PDF upload → parse → schema-driven extraction with confidence → the existing review queue, plus a firm-wide review queue page.
2. **Postgres and MCP:** move the store to Postgres behind the same actions, and serve the 14 query tools as an MCP server so chat (or Claude directly) runs against the real database with row-level permissions.
3. **Covenant depth:** multiple covenant types, EBITDA add-back rules, and downside cases feeding cushion automatically.
4. **Closing:** checklist, conditions precedent, and a comparison of the approved terms with the signed terms, so the IC-approved set is checked against the final credit agreement.
5. **Controls:** SSO, per-deal teams, information walls with a wall-crossing log, and Word export of the IC memo.
